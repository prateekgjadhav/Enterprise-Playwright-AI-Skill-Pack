Enterprise Playwright AI Skill Pack

Forty-seven narrow skills and one orchestrator that turn any request about Playwright testing — functional, operational, security or risk — into the same disciplined path: explore, choose the right skills, follow the rules, verify, run, and report with evidence.

  1. Requestfrom a person or CI
  2. OrchestratorCLAUDE.md
  3. Explorereuse what exists
  4. Select skillsrouting table
  5. Governancerules as tools
  6. Verifynpm run verify
  7. Executenarrowest tests
  8. Evidenceresults you can check

Each skill does one job and names the requests it is not for, so two skills rarely compete for the same task. The orchestrator holds the workflow, the routing table and the non-negotiables; the hooks make the rules impossible to skip. Everything is generic — project-specific values live in .agents/qa.config.json.

The security skills are defensive and authorised-only: they prove an application, pipeline, configuration or design the team owns enforces its own controls; they never exploit, and never run against production. Risk work is evidence-based: security-posture-management manages vendor, CVE and compliance risk from scanner output, SBOMs, vendor-supplied evidence and public threat intelligence, and never scans a vendor’s systems.

Install and first run

The pack is generic — it reads your repository and sets itself up, so it works on a fresh repo or an existing Playwright suite. It ships as one zip that unpacks to a single folder, enterprise-playwright-ai-skill-pack/.

  1. Unzip the pack anywhere and, from that folder, run ./setup.sh path/to/your-repo (run it with --dry-run first to preview). It copies the pack in without overwriting anything: a file that differs from yours is left alone, and the pack’s copy is saved beside it as .pack-new. If you already have a .claude/settings.json, it offers to add the pack’s permissions and hooks to it; if you already have a CLAUDE.md, it offers to import the orchestrator with one line instead of replacing the file. Both keep a backup. It finishes by linking the skills into .claude/skills (one copy in .agents/skills serves every agent tool) and checking them.
  2. Open the repository in Claude Code and ask the agent to set up the project. project-setup discovers your stack read-only, writes the detected values into .agents/qa.config.json, and scaffolds only what is missing (a verify script, the ESLint five-rule config, tsconfig, playwright.config.ts, @fixtures and one example spec). It never overwrites your config without showing a diff.
  3. It finishes by running npm run verify and a smoke test and reporting what it found and created — at which point the governance hooks are live.
  4. Ask for something small, such as add a smoke test for the login page, and confirm the reply ends with the evidence block.
  5. For risk and compliance work, add the security block to the config (see Configuration) and start with a scoped question, such as which of our open CVEs are on the KEV list?

To update, unzip the new pack and run ./setup.sh --force path/to/your-repo: pack files that changed are replaced and backed up first, and your own CLAUDE.md, AGENTS.md and .claude/settings.json are still merged, never replaced. The pack’s README.md also covers starting a new repository from the pack and removing it.

Configuration

Project values live in one file, .agents/qa.config.json. project-setup fills in the core blocks from what it discovers; agent-telemetry and security-posture-management each add an optional block when you start using them. A populated example with both added:

{
  "project":      { "name": "my-app", "environments": ["dev", "staging"], "defaultEnv": "staging", "protectedHosts": ["www.example.com"] },
  "framework":    { "root": ".", "playwrightVersion": "1.64.1", "testIdAttribute": "data-testid", "fixturesImport": "@fixtures" },
  "requirements": { "adapter": "files", "mcpServer": null },
  "knowledge":    { "mcpServer": null, "minScore": 0.75 },
  "telemetry":    { "enabled": false, "otlpEndpoint": null, "llmDashboard": null, "sampleRate": 1.0, "redactFields": ["prompt", "response", "headers.authorization"], "retentionDays": 30 },
  "security":     { "frameworks": ["SOC2", "ISO27001"], "slaDays": { "P1": 7, "P2": 30, "P3": 90, "P4": 180 }, "epssThreshold": 0.1,
                    "riskRegister": "security/risk-register.yaml", "vendorRegister": "security/vendors.yaml", "sbomDir": "security/sbom", "mcpServer": null },
  "ci":           { "platform": "github-actions" },
  "gates":        { "fileDefects": "ask", "knowledgeWrite": "ask", "dashboardPush": "ask", "securityScan": "ask", "updateBaselines": "ask", "riskAcceptance": "ask" }
}

The gates decide which actions always need a person: filing defects, writing to the knowledge base, pushing to dashboards, running security scans, updating visual baselines and accepting a risk. Telemetry is opt-in and self-hosted; it records decision metadata, never secrets or target data. The security block sets the frameworks in scope, the SLA in days for each priority, the EPSS threshold, and where the registers and SBOMs live.

Orchestration

CLAUDE.md is the orchestrator: it runs the same eight steps for every request, across every domain — development, operations, Penetration Testing and risk alike — and decides which skills do the work. It never does the work itself; the skills do.

Step 0 — set up first. On an unfamiliar repository (or when .agents/qa.config.json is unpopulated or npm run verify is absent), the orchestrator routes to project-setup before anything else: it reads the repo read-only, writes the detected values into qa.config.json, and scaffolds only what is missing so the governance hooks can actually run. The pack assumes nothing — it discovers the stack, then creates what it needs.

  1. Understand the request and fetch the ticket if a tracker is connected.
  2. Explore the repository: existing pages, modules, fixtures and nearby specs, so nothing is duplicated.
  3. Select skills from the routing table: usually one primary and one or two supporting. Security requests go to an umbrella skill, which delegates to the focused checks; risk, compliance and posture requests go to security-posture-management.
  4. Do the work bottom-up: data, then pages, modules, fixtures, specs.
  5. Apply governance: the hooks lint every edited file as it is written.
  6. Verify with npm run verify (lint, types, governance, dependency rules).
  7. Execute the narrowest tests that cover the change, with repeats for new tests.
  8. Report with the evidence block: request, skills used, changes, verification, results, artifacts, risks.

When two skills seem to fit, the orchestrator prefers the one whose “Not for” line doesn’t exclude the request. The routing table and the skill manifest are generated from the skills themselves, so routing cannot drift as the pack grows.

Governance rules

Five rules are enforced by tools, not memory. Each fails the build.

RuleEnforced by
No XPathESLint ban on locator() strings starting with xpath= or //, plus the governance script
No waitForTimeout (and no network-idle waits or sleeps)ESLint Playwright rules
No duplicate page objectsThe governance script: one class and one route per page
No hard-coded test dataThe governance script flags literal emails, card numbers, passwords and absolute URLs
Dependency injectionESLint bans new …Page() in specs; specs import only fixtures

Around them sit the supporting rules: web-first assertions only, no assertions inside page objects, one priority tag and one feature tag per test, and a CI image that matches the installed Playwright version. Security skills add their own non-negotiables: authorised non-production targets, non-destructive checks, and no exploit output or secrets. Risk work adds two more: every CVE, KEV and EPSS fact carries its source and date, and only a named person can accept a risk. Waivers need a comment naming the rule, the reason and a ticket; stale waivers fail lint. The governance script is scripts/governance-check-all.mjs, which npm run verify runs; a waiver for it reads // governance-disable-next-line <rule> -- <reason> (<ticket>).

Two hooks make the rules unavoidable: one lints every TypeScript file the moment it is edited, the other blocks “done” while npm run verify fails. A skill-evaluation gate does the same for the skill set itself.

Penetration Testing

A first-class category of 24 defensive, authorised-only security skills. Each assesses something the team owns and is authorised to test, and all inherit the pack non-negotiables: authorised non-production targets only, non-destructive checks, no exploit detail or credentials in output, and scans gated by gates.securityScan. They prove controls hold and produce findings and reports — they are not exploitation tools, and they complement rather than replace a security team’s manual review. Route through an umbrella (web-app-security-assessment, security-regression-suite, cloud-security-review) and it delegates to the focused checks below. Their findings flow on to security-posture-management, which tracks each one to closure.

Risk, compliance & posture

One programme-level skill that sits above the Penetration Testing checks. It scans nothing itself: it takes their findings, the SBOMs they generate, the evidence vendors supply and public threat intelligence, and keeps one deduplicated risk register in which every item has a priority, an owner and a deadline, and every claim has a source.

SkillPurposeReach for it when you want to…
security-posture-managementVendor risk, SBOM inventory, the CVE lifecycle, threat intelligence, compliance mapping and posture metricsassess a vendor, answer “are we affected?”, set CVE SLAs and exceptions, prepare audit evidence, report posture

What it covers

AreaWhat the skill doesWhat you get
Vendor riskTiers each vendor by the data and access it has, drafts requests for the evidence that tier needs (SOC 2 Type II or ISO 27001, a questionnaire, SBOM and VEX, contract clauses) for a person to send, and reviews what comes backA vendor register with tier, rating, gaps and next review date
SBOMKeeps one SBOM per shipped release plus every vendor SBOM, checks the minimum elements, and keeps each VEX beside its SBOMAn inventory that answers “do we ship this component?” in minutes
CVE managementMerges every scanner’s findings into one record per CVE, component and asset; sets priority, SLA date and owner; tracks exceptions to expiryA risk register with due dates, owners and VEX state
Threat intelligenceAdds the CISA KEV listing and FIRST EPSS score to every record, dated, and re-matches the stored SBOMs nightlyExploitation-first priorities, and an alert when a shipped CVE joins KEV
ComplianceMaps the work to SOC 2, ISO/IEC 27001, NIST CSF and SSDF, PCI DSS and the EU Cyber Resilience ActA control, evidence and gap matrix an auditor can sample
Security postureComputes KEV exposure, SLA compliance, past-SLA backlog, exception health and coverageTrended metrics for the release go/no-go

How it prioritises

PriorityRule (first match wins)Default SLA
P1Affected and listed in CISA KEV, or exploitation confirmed by the vendor7 days
P2CVSS 9.0 or above, or EPSS at or above the threshold, on a reachable path in a production or internet-facing asset30 days
P3CVSS 7.0–8.9, or the P2 conditions on an internal-only asset90 days
P4Anything else that is affected180 days

A VEX not_affected statement closes a record only with a justification. SLAs come from security.slaDays; with PCI DSS in scope, keep critical-ranked vulnerabilities inside one month (requirement 6.3.3). An exploited vulnerability in a product sold in the EU may also trigger Cyber Resilience Act Article 14 reporting, which has applied since 11 September 2026: the skill flags the case to its owner the same day and never files the report itself.

It never scans, probes or logs in to a vendor’s systems, and never fetches or runs exploit code. Every CVE, KEV and EPSS fact carries its source and date, and a feed that fails to load is an error, never “not listed”. Accepting a risk needs a named person (gates.riskAcceptance). Compliance output maps evidence to controls; it never claims the organisation is compliant.

Skills working together

You askWhat happens
“Automate the acceptance criteria for PROJ-123”playwright-test-generation plans cases; endpoint cases go to api-testing; missing screens to page-object-engineering with selectors from locator-strategy; data from test-data-management; framework-governance checks the result.
“Run a security assessment of checkout before release”web-app-security-assessment scopes it and maps the feature to the OWASP Top 10; auth-access-control-review, injection-handling-review, xss-output-encoding-review and security-headers-review run non-destructive checks against staging; dependency-vulnerability-audit and secrets-detection cover the supply chain; pentest-report-generator turns the findings into a report with CVSS and remediation; security-posture-management then tracks each finding to closure against its SLA.
“A critical CVE is in the news — are we affected?”security-posture-management re-matches the advisory against every stored SBOM, including vendor SBOMs, applies VEX and adds the KEV and EPSS context. Affected components go to dependency-vulnerability-audit or docker-security-review for the fix, each with a priority, SLA date and owner; vendors that ship the component are asked for their VEX by a person; and if the vulnerability is exploited in a product sold in the EU, the case is flagged for Cyber Resilience Act reporting.
“We’re onboarding a payments vendor”security-posture-management tiers the vendor as critical and drafts the evidence request — SOC 2 Type II report, questionnaire, SBOM and VEX, breach-notice clause — for a person to send. It reviews what comes back and records the rating, gaps and next review, without scanning or probing anything on the vendor’s side.
“Get us ready for the SOC 2 audit”security-posture-management builds the control, evidence and gap matrix from the risk register, exceptions, vendor reviews, scan history and CI gates, and turns each gap into a ticket; pentest-report-generator supplies the latest assessment report; reporting-analytics publishes the summary once approved. Whether the audit passes stays the auditor’s call.
“Is checkout ready to ship?”reporting-analytics combines functional results with performance-testing budgets, accessibility-testing scans, security-regression-suite findings, security-posture-management’s open risk (no open P1 or past-SLA item) and sre-reliability error-budget status into a go or no-go summary.
“Why did the agent pick that skill, and what did it cost?”agent-telemetry shows the run as spans with the routing decision and LLM-call tokens/cost; skill-evaluation explains overlaps and checks the routing table is still in sync.
“Did the model or prompt change hurt output quality?”deepeval scores the generated tests, migrations and reports against golden datasets with LLM-as-judge and tool-use metrics and fails CI on a regression, while agent-telemetry shows the matching cost and latency — distinct from skill-evaluation, which only checks the skills themselves are well-formed.

Everything except README.md, setup.sh and docs/ is copied into your repository. Skills follow one house shape: spec-compliant frontmatter (name, description, and metadata with tier and pack), non-negotiables, a procedure, working templates and a definition of done. scripts/check-skills.mjs checks that shape, the routing and the manifest, and skill-validation.yml runs it in CI.

Definition of done

  • The reply names the skills it used and ends with the evidence block.
  • npm run verify passes; no unexplained waivers; the skill-evaluation gate is green.
  • New or changed tests passed the commands shown, including repeats for new tests.
  • Nothing was duplicated: no second page object for a route, no overlapping skill.
  • Security work stayed defensive and authorised: non-production target, non-destructive, no exploit output.
  • Risk work stayed evidence-based: facts sourced and dated, no vendor system scanned, no risk accepted without a named approver, no compliance claimed.
  • Gated actions happened only with approval.
